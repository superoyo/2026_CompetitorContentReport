# 2026 Competitor Content Report

Pipeline สร้างรายงาน Engagement รายเดือนของเพจคู่แข่งบน Facebook
ผลลัพธ์เป็น **PPTX สรุป Top 5 ของแต่ละเพจ** และ **HTML dashboard** แบบ self-contained

## เพจที่ติดตาม — มาจาก Agency Intelligence

เดิมเป็นรายชื่อ 8 เพจตายตัวในโค้ด (กลุ่ม PAO) ตอนนี้มาจากหน้า **Brand Asset**
ของ Product Group ที่เลือก ใน Agency Intelligence — ที่นั่นคือที่ที่มีการแก้ไขจริง
การเก็บสำเนาไว้ที่นี่ด้วยทำให้รายงานล้าสมัยเงียบ ๆ ทุกครั้งที่มีคนแก้ที่โน่น

```
dropdown มุมซ้ายบน  →  เลือก Product Group
      ↓
popup ติ๊กเลือกแบรนด์  →  จำไว้ต่อกลุ่ม ครั้งต่อไปเปิดมาติ๊กไว้ให้เลย
      ↓
ตารางขึ้นชื่อแบรนด์ ค่ายังว่าง  →  กดโหลดข้อมูลใหม่จึงจะมีตัวเลข
```

รับเฉพาะแบรนด์ที่มีลิงก์ Facebook — แบรนด์ที่ยังไม่ใส่ลิงก์จะไม่ปรากฏในรายการ
`key` ของแต่ละแบรนด์มาจาก path ของเพจ (`/PaoSociety/` → `PaoSociety`) ไม่ใช่ชื่อ
ที่ผู้ใช้พิมพ์ เพราะชื่อแก้เมื่อไหร่ก็ได้ แต่คีย์ต้องคงที่ ไม่งั้นข้อมูลข้ามเดือน join กันไม่ติด

| ตัวแปร | ค่า |
|---|---|
| `AGENCY_API_BASE` | เช่น `https://agencyintelligence.fareastfameline.com` |
| `AGENCY_SERVICE_KEY` | ต้องตรงกับ `REPORT_SERVICE_KEY` ฝั่ง Agency Intelligence |

ไม่ตั้งค่าสองตัวนี้ = dropdown จะบอกว่าดึงรายชื่อกลุ่มไม่ได้ ส่วนการรันจาก command
line ยังใช้รายชื่อ 8 เพจเดิมได้ตามปกติ

## ฐานข้อมูล — จำว่าดึงเดือนไหนไปแล้ว

Railway ใช้ filesystem แบบชั่วคราว ไฟล์ที่สร้างจะหายเมื่อ redeploy แต่ปฏิทินต้อง
ตอบให้ได้ว่ากลุ่มนี้มีข้อมูลเดือนไหนแล้ว ผลลัพธ์แต่ละเดือนจึงเก็บลง Postgres

| ตาราง | เก็บอะไร |
|---|---|
| `ccr_reports` | ผลของ (กลุ่ม, เดือน) — ตัวเลขทั้งหมดพร้อมรูปฝังเป็น data URI |
| `ccr_selection` | แบรนด์ที่ติ๊กไว้ของแต่ละกลุ่ม |

**Postgres ตัวไหนก็ได้** — ระบบนี้อ่านข้อมูลของ Agency Intelligence ผ่าน HTTP
(`agency_api.py`) ไม่ได้ยิง SQL เข้าตารางของระบบนั้นเลย `DATABASE_URL` จึงใช้แค่
เก็บสองตารางข้างบนของตัวเอง ไม่ต้องเป็น DB เดียวกับ Agency Intelligence

บน Railway ให้ตั้งเป็น **variable reference** ไม่ใช่พิมพ์ค่าจริงลงไป:

```
DATABASE_URL = ${{Postgres.DATABASE_URL}}
```

(`Postgres` = ชื่อ service Postgres ใน project เดียวกัน) การพิมพ์ค่าเต็มลงไปจะพัง
เงียบ ๆ เมื่อรหัสถูก rotate — อาการคือ `password authentication failed for user "postgres"`
ถ้าจะใช้ DB ร่วมกับ Agency Intelligence ที่อยู่คนละ project ต้องใช้
`DATABASE_PUBLIC_URL` ของฝั่งนั้น เพราะ `*.railway.internal` คุยข้าม project ไม่ได้

ไม่ตั้งค่า **หรือต่อไม่ได้** = ถอยไปเก็บเป็นไฟล์ใน `/tmp` ซึ่งหายไปกับ container
เว็บยังใช้งานได้ปกติ แต่ header จะขึ้นเตือนพร้อมเหตุผลจริงจาก Postgres —
ไม่แกล้งทำเป็นว่าเก็บถาวรได้ และไม่ล้มทั้ง container เพราะ DB ตัวเดียว

สถานะของเดือนบนปฏิทิน:

| สถานะ | หน้าตา | กดแล้วเกิดอะไร |
|---|---|---|
| มีข้อมูล | ขอบเขียว | เปิดข้อมูลเดือนนั้นทันที ไม่เสียค่า Apify |
| ยังไม่มี | ขอบจาง | บอกว่าต้องกดโหลดข้อมูลใหม่ก่อน |
| ยังไม่ถึง | จางลง กดไม่ได้ | — |

กดโหลดข้อมูลใหม่ทับเดือนที่มีข้อมูลอยู่แล้ว จะถามยืนยันก่อน เพราะข้อมูลเดิม
จะถูกแทนที่และมีค่าใช้จ่าย Apify

## Pipeline

| ไฟล์ | หน้าที่ |
|---|---|
| `scrape_apify.py` | ดึงโพสต์จาก Facebook ผ่าน Apify actor |
| `process.py` | กรองตามเดือน คำนวณ engagement จัดอันดับ |
| `crop.py` | จัดการรูปภาพประกอบโพสต์ |
| `build_slides.py` | สร้างสไลด์ PPTX (Top 5 ต่อเพจ) |
| `dashboard_data.py` | รวมผลประมวลผลเป็น payload ก้อนเดียวที่หน้าเว็บใช้ (รูปฝังในตัว) |
| `build_dashboard.py` | render payload เป็น HTML — จากเดือนที่เพิ่งประมวลผล หรือจากที่เก็บไว้ |
| `analyse.py` | ให้ Claude เขียนบทวิเคราะห์จากตัวเลขของเดือนนั้น |
| `report_config.py` | บทวิเคราะห์เขียนมือของ PAO พ.ค. 2569 — fallback เมื่อไม่มีที่ generate |
| `brandset.py` | รายชื่อแบรนด์ของรอบนี้ (`$BRANDSET_JSON`) — เดิมเป็น literal ในสามไฟล์ |
| `agency_api.py` | อ่าน Product Group + คู่แข่งจาก Agency Intelligence |
| `store.py` | เก็บผลแต่ละ (กลุ่ม, เดือน) ลง Postgres |

## วิธีรัน

Apify token ส่งผ่าน environment variable ทุกครั้ง — **ไม่ hardcode ลงไฟล์**

```bash
export APIFY_TOKEN=apify_api_xxxxxxxx
python3 scrape_apify.py
python3 process.py
python3 build_slides.py
python3 build_dashboard.py
```

## เลือกเดือนและโหลดข้อมูลใหม่

มุมขวาบนของ dashboard มีปฏิทินเลือกเดือน (📅) และปุ่ม **โหลดข้อมูลใหม่**
เลือกเดือนแล้วกดปุ่ม `server.py` จะรัน pipeline ทั้งสามขั้น
(scrape → process → build) สำหรับเดือนนั้น แล้วรีเฟรชหน้าเมื่อเสร็จ

ปฏิทินเขียนขึ้นเองไม่ได้ใช้ `<input type="month">` เพราะ Safari บน macOS
ไม่มี native month picker เดือนที่ยังไม่มาถึงจะกดไม่ได้

ค่าเริ่มต้นคือ **เดือนที่จบแล้วล่าสุด** (เปิดหน้าเว็บเดือนกันยายน ปฏิทินจะตั้งไว้ที่
สิงหาคมให้เลย) เพราะเดือนปัจจุบันยังไม่จบ ตัวเลขจะไม่ครบเดือน หากหน้าเว็บที่เปิดอยู่
สร้างจากเดือนอื่น จะมีข้อความบอกว่าหน้านี้แสดงเดือนไหนและปฏิทินตั้งไว้เดือนไหน

เดือนที่ใช้มาจาก `$REPORT_MONTH` (รูปแบบ `YYYY-MM`) ซึ่ง `month_util.py`
เป็นตัวกลางแปลงเป็นช่วงวันที่ scrape, ตัวกรองโพสต์ และป้ายชื่อเดือนบนหน้าเว็บ
ทั้งหมด — รันจาก command line ก็ได้:

```bash
REPORT_MONTH=2026-06 APIFY_TOKEN=apify_api_xxx python3 scrape_apify.py
REPORT_MONTH=2026-06 python3 process.py
REPORT_MONTH=2026-06 python3 build_dashboard.py
```

## ตรวจว่าเชื่อมครบหรือยัง

ระบบนี้พึ่งบริการภายนอกสี่ตัว การจะรู้ว่าตั้งค่าครบไหมโดยกดดึงข้อมูลจริง
มีราคาแพงและช้า — และบอกได้แค่ตัวแรกที่พัง `/api/selftest` ยิงจริงทุกตัวแล้ว
รายงานทีเดียว

```bash
curl -s -H "X-Refresh-Key: <REFRESH_KEY ของคุณ>" \
  https://2026competitorcontentreport-production.up.railway.app/api/selftest
```

| ตรวจอะไร | วิธีตรวจ | ค่าใช้จ่าย |
|---|---|---|
| Postgres | นับแถวใน `ccr_reports` จริง | ฟรี |
| Agency Intelligence | เรียก `/report-feed/groups` แล้วนับกลุ่มที่เห็น | ฟรี |
| Apify | เรียก `/users/me` — คืนชื่อบัญชีและแผน | ฟรี |
| Claude | ส่งข้อความสั้นที่สุดที่โมเดลรับ | ~$0.0001 |

ตั้งใจให้ยิงของจริงทุกตัว ไม่ใช่เช็คว่า "ตัวแปรถูกตั้งไว้ไหม" — คีย์ที่พิมพ์ผิด
ก็ถือว่าถูกตั้งไว้เหมือนกัน ข้อความที่ได้กลับมาเป็นเหตุผลจริงจากปลายทาง เช่น
`Apify ปฏิเสธ token (401)` หรือ `password authentication failed`

ต้องมี `X-Refresh-Key` เพราะ endpoint นี้บอกว่าต่ออะไรอยู่บ้าง และเรียก Claude จริง

## บทวิเคราะห์ — Claude เขียนจากตัวเลขของเดือนนั้น

`analyse.py` เป็นขั้นหนึ่งใน pipeline ส่งตัวเลขจริงของทุกเพจ + แคปชั่น Top 5
ให้ Claude แล้วให้เขียน 3 กล่องกลับมา: บทวิเคราะห์รายเพจ, Top 3 คอนเทนต์,
และ KEY LEARNING (เขียนให้แบรนด์ที่ปักหมุดไว้ในหน้า Brand Asset)

ยิงครั้งเดียวต่อกลุ่ม ไม่ใช่ทีละเพจ เพราะข้อสังเกตที่มีค่าคือการเปรียบเทียบ
("สูงสุดในกลุ่ม", "โพสต์ถี่กว่าเจ้าอื่นสามเท่า") ซึ่งดูเพจเดียวไม่ออก
ผลลัพธ์บังคับด้วย JSON schema รูปร่างจึงเพี้ยนไม่ได้

| ตัวแปร | ค่า |
|---|---|
| `ANTHROPIC_API_KEY` | รับ `ANTHOPIC_KEY` ด้วย (ชื่อที่ตั้งไว้แล้วบน Railway ฝั่ง Agency Intelligence) |
| `ANTHROPIC_WORKSPACE_ID` | ตั้งเฉพาะเมื่อคีย์เป็น identity token ที่ผูก workspace — API key ธรรมดา (`sk-ant-api…`) ไม่ต้องตั้ง |
| `ANALYSIS_MODEL` | ค่าเริ่มต้น `claude-opus-5` |
| `ANALYSIS_EFFORT` | `low` … `max` (ค่าเริ่มต้น `high`) |

**ไม่ตั้งคีย์ = ข้ามขั้นนี้** ตัวเลข กราฟ รูป และ Top 5 ไม่กระทบ กล่องวิเคราะห์
จะถูกซ่อน (ไม่ใช่ขึ้นหัวข้อแล้วว่างเปล่า) — เช่นเดียวกับตอนเรียก API ไม่สำเร็จ
ค่าใช้จ่ายต่อครั้งขึ้น log ของรอบนั้น (~$0.10 ที่ Opus 5 สำหรับ 5 เพจ)

แคปชั่นโพสต์เป็นเนื้อหาจากอินเทอร์เน็ต ส่งเข้าไปในฐานะ **ข้อมูล** และ system
prompt สั่งไว้ชัดว่าถ้าในแคปชั่นมีข้อความสั่งอะไร ให้เพิกเฉย

> **ของเก่าใน `report_config.py`** ยังอยู่ เป็นงานเขียนมือของกลุ่ม PAO เดือน
> พฤษภาคม 2569 ใช้เป็น fallback เมื่อไม่มีบทวิเคราะห์ที่ generate ไว้ และแสดง
> **เฉพาะเมื่อรายงานตรงกับที่เขียนไว้** (เดือนตรงกับ `AUTHORED_MONTH` และเพจ
> ตรงกับที่เขียนถึง) เพราะบทวิเคราะห์ของ PAO ใต้ชื่อ Shokubutsu ผิดพอ ๆ กับ
> บทวิเคราะห์เดือน พ.ค. ใต้ป้ายเดือน ส.ค. ส่วนที่ Claude เขียนไม่ต้องกรอง —
> มันถูกเขียนให้กลุ่มและเดือนนั้นโดยตรงอยู่แล้ว
>
> การกรองเกิดตอน **render** ไม่ใช่ตอนเก็บ เดือนที่เก็บไว้ก่อนหน้าจึงสะอาดตามไปด้วย
> โดยไม่ต้องดึงข้อมูลใหม่

ปุ่มทำงานได้เฉพาะเมื่อเปิดจากเว็บที่รัน `server.py` (เช่น Railway) — บน GitHub Pages
เป็นไฟล์นิ่งจึงไม่มี backend ปุ่มจะถูกปิดพร้อมข้อความอธิบาย

ปุ่มที่ใช้เงินมีสองปุ่ม — **โหลดข้อมูลใหม่** (Apify) และ **เขียนบทวิเคราะห์** (Claude)
ทั้งคู่ล็อกด้วย `REFRESH_KEY` เดียวกัน และขึ้นรูป 🔑 จนกว่า session นี้จะมีคีย์ที่
เซิร์ฟเวอร์รับแล้ว คีย์ที่กรอกถูกตรวจกับเซิร์ฟเวอร์ทันที (`/api/verify-key`) ไม่ใช่
รอให้งานปฏิเสธทีหลัง — คีย์ผิดจะบอกตรงนั้นและไม่ถูกจำไว้

**Apify token อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น ไม่เคยถูกส่งไปหน้าเว็บ** และเพราะเว็บเปิด
สาธารณะ endpoint จึงต้องใช้ shared secret กันคนอื่นมากดใช้ credit

ตั้ง environment variable บน Railway:

| ตัวแปร | ค่า |
|---|---|
| `APIFY_TOKEN` | Apify API token |
| `REFRESH_KEY` | รหัสอะไรก็ได้ที่ตั้งเอง — ต้องกรอกครั้งแรกที่กดปุ่ม |

Endpoint ที่ปุ่มเรียก:

| Method | Path | ผลลัพธ์ |
|---|---|---|
| `GET` | `/?group=&month=` | หน้า dashboard ของกลุ่มและเดือนนั้น |
| `GET` | `/api/groups` | Product Group ทั้งหมด (ผ่าน Agency Intelligence) |
| `GET` | `/api/groups/<id>/brands` | แบรนด์ของกลุ่ม + ที่ติ๊กไว้ครั้งก่อน |
| `POST` | `/api/groups/<id>/brands` | บันทึกแบรนด์ที่ติ๊ก |
| `GET` | `/api/groups/<id>/months` | เดือนที่มีข้อมูลแล้ว |
| `POST` | `/api/refresh` | เริ่มงาน (ต้องมี header `X-Refresh-Key`) |
| `GET` | `/api/status` | สถานะงานปัจจุบัน |
| `GET` | `/api/verify-key` | ตรวจ Refresh key ตอนผู้ใช้กรอก |
| `POST` | `/api/analyse` | เขียนบทวิเคราะห์ให้เดือนที่มีข้อมูลแล้ว (ไม่เรียก Apify) |
| `GET` | `/api/selftest` | ตรวจการเชื่อมต่อทุกบริการ (ต้องมี `X-Refresh-Key`) |

> Railway ใช้ filesystem แบบชั่วคราว หน้าเว็บที่ render แล้วจึงเป็นแค่ cache ใน `/tmp`
> ตัวข้อมูลจริงอยู่ใน Postgres — เปิดเดือนเดิมอีกครั้งจะ render ใหม่จากที่เก็บไว้
> ไม่เรียก Apify ซ้ำ

## ปุ่มดาวน์โหลด PPT

ปุ่มดาวน์โหลดสไลด์ทำงานกับ **เดือนที่เลือกในปฏิทิน** ไม่ใช่เดือนที่หน้าเว็บแสดงอยู่
เปลี่ยนเดือนในปฏิทินแล้วปุ่มจะเปลี่ยนเป้าหมายทันที (ปฏิทินส่ง event `fbdash:month`
ให้ปุ่มรับ) ป้ายปุ่มบอกเดือนที่จะได้ตลอด เช่น `PPT ส.ค. 2569 (2.5 MB)`

ถ้าไฟล์ไม่มี (เช่น container ถูก redeploy) ปุ่มจะเปลี่ยนเป็น **สร้างไฟล์ PPT**
ซึ่งเรียก `GET /api/pptx?month=YYYY-MM` ให้เซิร์ฟเวอร์ render สไลด์จากข้อมูลที่
ประมวลผลไว้แล้ว — รันแค่ `build_slides.py` **ไม่เรียก Apify จึงไม่มีค่าใช้จ่าย**

endpoint ตรวจว่าข้อมูลบนเซิร์ฟเวอร์เป็นเดือนเดียวกับที่ขอจริงไหม (จาก `month`

เดือนไหนอยู่ กันการสร้างสไลด์ที่ชื่อเดือนหนึ่งแต่เนื้อหาเป็นอีกเดือน

## หมายเหตุการเรียก Claude API ใน analyse.py

เรียกแบบ **streaming** (`messages.stream` + `get_final_message`) ไม่ใช่
`messages.create` เพราะ `MAX_TOKENS = 64000` — ค่าขนาดนี้ถ้าไม่ stream จะชน
HTTP timeout ของ SDK

adaptive thinking ถูกคิดเป็น output token ด้วย รอบ 8 เพจเคยใช้ไป 15,384 token
ซึ่งเกือบเต็มเพดานเดิมที่ 16,000 พอ prompt ขอคำบรรยายละเอียดขึ้น JSON จึงถูกตัด
กลางทางและ parse ไม่ได้

โค้ดแยกกรณี `stop_reason == "max_tokens"` ออกมาบอกตรง ๆ ว่าชนเพดาน พร้อมจำนวน
token ที่ใช้ไป — ก่อนหน้านี้รายงานรวมเป็น "อ่านผลลัพธ์เป็น JSON ไม่ได้" ทำให้
เข้าใจผิดว่า schema พัง

## กล่องสรุปวิเคราะห์คอนเทนต์ (Top 3 & ภาพรวมเดือน)

`analyse.py` เขียนสองฟิลด์นี้ให้เป็น **คำบรรยายเชิงเนื้อหาล้วน ไม่มีตัวเลข**

| ฟิลด์ | ต้องเขียนถึง | ห้ามมี |
|---|---|---|
| `top3` | คอนเทนต์อะไร สื่อสารอะไร สินค้าตัวไหน | ยอด engagement / ไลก์ / คอมเมนต์ / แชร์ / วันที่ / อันดับเป็นเลข |
| `overview` | เน้นแนวไหน หลากหลายเพียงใด มีประเภทไหนบ้าง | จำนวนโพสต์ และยอด engagement |

`overview` ใช้คำบอกปริมาณเชิงคุณภาพได้ ("เป็นส่วนใหญ่", "มีประปราย", "แทบไม่มี")
และถ้าแคปชั่นไม่ระบุสินค้าชัดเจน ให้เขียนว่าเป็นคอนเทนต์ของแบรนด์โดยรวม
ห้ามเดาชื่อสินค้า

`metric_free()` คอยตรวจผลลัพธ์ทุกรอบ ถ้ายังมีตัวเลขที่อ่านเป็นเมตริกหลุดมา จะขึ้น
`WARN` ใน log ของรอบนั้น — เป็นการเตือนไม่ใช่การแก้ข้อความ เพราะการตัดตัวเลข
อัตโนมัติจะไปทำลายชื่อสินค้าที่มีเลขอยู่จริง เช่น "ซุปเปอร์ 3 สูตร"

## SUMMARY COMPETITOR

ก้อนก่อนกล่องล่างสุด แบ่งสองฝั่ง

**ซ้าย** ตารางเดียวกับ Metrics Overview แต่ติดเหรียญอันดับ 1–3 ของแต่ละคอลัมน์
(เขียว/ทอง/แดง) และไฮไลต์แถวของแบรนด์ที่เราดูแล จัดอันดับแบบ competition
ranking — คะแนนเท่ากันได้อันดับเดียวกันแล้วข้ามอันดับถัดไป (1, 1, 3) เพจที่ไม่มี
ค่าในคอลัมน์นั้นจะไม่ได้อันดับ ไม่ถูกนับเป็นศูนย์

**ใต้ตาราง** กล่องเต็มความกว้าง บอกตำแหน่งของแบรนด์เราทีละคอลัมน์
(`ทำได้ X (อันดับ N จาก M)`) เรียงเป็นกริดที่ยืดตามความกว้างจอ ต่อด้วยบทวิเคราะห์
ของเดือนนั้นจาก `analyse.py` แบ่งเป็นสองคอลัมน์

ตัวเลขในตารางไม่มีหน่วยต่อท้าย — คอลัมน์ตัวเลขอ่านเร็วกว่าเมื่อไม่มีคำซ้ำทุกแถว
ส่วนกล่องด้านล่างใส่หน่วยไว้ เพราะค่าอยู่ในประโยค

แบรนด์ที่ถือเป็น "ของเรา" มาจาก flag `owned` ใน brandset ถ้าไม่ได้ระบุ จะใช้เพจ
ที่ `analyse.py` เขียน keylearning ให้ เพื่อให้ตารางกับแผงขวาไม่พูดถึงคนละเพจ

กล่องท้ายหน้าแยกใบละเพจ เก็บตัวเลขที่ตาราง Metrics Overview ไม่ได้แสดงหลังเปลี่ยน
มาใช้คอลัมน์แบบรายงานอ้างอิง — Engagement รวม, ค่าเฉลี่ยต่อโพสต์, ฟอร์แมตที่ได้
Engagement เฉลี่ยสูงสุด, วันที่โพสต์แล้วเวิร์กที่สุด และ chip สัดส่วนคอนเทนต์ที่ลงจริง
(นับจาก `media_mix`) ทั้งหมดมาจาก payload เดิม ไม่ต้องดึงข้อมูลเพิ่ม

## Metrics Overview

ตารางหลักมี 9 คอลัมน์: Name, Page Performance Index, Followers, Follower Growth,
Number of posts / Reactions / comments / Shares และ Engagement

| คอลัมน์ | ที่มา |
|---|---|
| posts / Reactions / comments / Shares | นับจากโพสต์ที่ scrape มาได้ |
| Followers | `page_stats.py` ผ่าน actor `apify/facebook-pages-scraper` |
| Follower Growth | เทียบกับ `fans` ในรายงานเดือนก่อนที่เก็บใน Postgres |
| Engagement | `engagement รวม ÷ followers ÷ จำนวนวันในเดือน` (อัตราต่อวัน) |
| Page Performance Index | คะแนนรวมที่เราคิดเอง — ดูด้านล่าง |

**Page Performance Index ไม่ใช่สูตรของ Rival IQ** ซึ่งไม่เคยเปิดเผยวิธีคำนวณ
ของเราคือ `0.55 × อัตรา Engagement + 0.25 × การเติบโตผู้ติดตาม + 0.20 × จำนวนโพสต์`
โดยแต่ละตัวถูก scale เทียบช่วงค่าภายในกลุ่มแบรนด์นั้น แล้วแสดงเป็น 0–100
สูตรเขียนกำกับไว้ใต้ตารางบนหน้าเว็บด้วย เปลี่ยนได้ที่ `dashboard_data._ppi()`

เปอร์เซ็นต์แสดงเป็นเลขนัยสำคัญ 2 ตัว (`0.89%`, `0.092%`, `0.0015%`) เพื่อให้เพจที่
อัตราต่ำมากยังอ่านค่าได้ ไม่ถูกปัดเป็น `0.00%`

**Follower Growth ต้องมีเดือนก่อนที่ดึงไว้แล้วจริง** จำนวนผู้ติดตามเป็นค่าที่อ่าน
ณ เวลาที่ดึง ไม่ใช่ค่าเฉลี่ยของเดือน และ Facebook ไม่เปิดเผยยอดย้อนหลัง จึงย้อนไป
เก็บของเดือนที่ผ่านมาไม่ได้ — ถ้าย้อนไปกดดึงเดือนเก่าวันนี้ ตัวเลขที่ได้คือยอดของ
*วันนี้* ไม่ใช่ของเดือนนั้น การเทียบจะกลายเป็น ~0% ซึ่งไม่จริง

`_far_enough()` จึงไม่คำนวณ growth เมื่อ snapshot สองรอบห่างกันไม่ถึง 20 วัน
(`MIN_GROWTH_GAP_DAYS`) และขึ้นข้อความอธิบายเหนือตารางแทน
และถ้าดึงผู้ติดตามไม่สำเร็จ คอลัมน์ Followers / Growth / Engagement จะว่าง
พร้อมข้อความอธิบายเหนือตาราง แทนที่จะเดาตัวเลข
